# SPEC.md — 尤里亞的占卜計算器

## 1. Route

MVP 僅需：

```text
/yuria
```

可選 query：

```text
/yuria?objective=threshold&target=2700
```

## 2. 主要操作流程

1. 玩家設定推薦目標。
2. 玩家輸入已完成的選牌結果。
3. 玩家輸入本回合出現的藍 / 紫 / 紅 3 張候選牌。
4. 系統立即模擬並排序 3 張牌。
5. 玩家選定實際抽的牌，再回填是否啟用；進入下一回合。

第 5 回合完成後，改顯示最終分數區間與獎勵階段，不再顯示下一張推薦。

## 3. 推薦目標

### Highest EV
排序依據：`meanFinalScore`。

### Target Rate
排序依據：`P(finalScore >= target)`；相同時再比較平均分數。

預設 Target：1500（目前使用者測試目標）。獎勵參考門檻仍保留 1400 / 2000 / 2700。

### Stable
主要比較 P10，下分位相同時比較平均分數並扣除波動。

MVP 不使用抽象「AI 分數」。所有排序欄位都必須能回溯到模擬資料。

## 6. 卡片出現權重

第 1~4 次：

```text

```

第 5 次：

```text
分數卡 5
倍率卡 10

```

目前遊戲說明只提供類別權重。MVP 對「同類別內各卡是否等權」採假設，UI 必須在進階資訊顯示此假設。未來候選顏色依 A 版採各位置獨立等機率，可出現同色。

## 7. 計分

```text
FinalScore = floor(SUM × MULT × (1 + RED_BONUS))
```

### SUM
包含：
- 成功啟用的分數卡
- 失敗卡每張 +20
- 藍色級距
- 月亮
- 世界

### MULT

```text
MULT = 1
     + Σ 成功倍率卡
     + 紫色級距
     + 高塔追加
     + 星星
     + 太陽
```

### RED_BONUS
依成功紅卡數落入指定區間後再抽樣。

MVP 預設用整數百分比均勻抽樣；要做成可切換規則，避免未來實測證明不是此分布時需要重寫核心。

## 8. 尤里亞的祝福

規則描述：「套用卡片與顏色效果後，幸運分數或倍率的其中一個數位將隨機增加 1。」

目前缺乏足夠精確的數學定義，因此：

- MVP 預設不納入最終推薦。
- UI 顯示「祝福尚未建模」。
- 一旦取得可重現實測，新增 `BlessingModel`，不可直接修改基本公式。

每張候選牌至少顯示：

```text

Lv.5 達標率
Lv.6 達標率
Lv.7 達標率
風險標籤

```

Top 1 額外顯示「推薦」badge。

## 10. 模擬效能

MVP：每張牌 10,000 次；總 30,000 次 rollout。第 5 回合在整數紅色模型下改用完整終局分布，不以抽樣次數冒充精確結果。

目標：
- Desktop P95 < 800 ms
- 中階手機 P95 < 1.5 s
- UI 主執行緒不可長時間凍結

使用 Web Worker；輸入變更採 120~200 ms debounce。

若手機效能不足，可先顯示 2,000 次快速結果，再補到 10,000 次並更新信賴區間。

## 11. 錯誤與可信度

推薦卡旁顯示：

```text
模型狀態：
✓ 已驗證公式
△ 未驗證：太陽自計數
△ 假設：類別內等權
△ 未建模：尤里亞祝福
```

不得使用「99% 準確 AI」等無實測依據文案。

## 12. RWD

### Mobile < 768px
- 單欄
- 候選卡以 3 張水平卡或可橫滑卡呈現
- 高階統計預設收合
- 底部 sticky「確認選擇」

### Desktop >= 1024px
- 左：本局歷史與狀態
- 中：3 張候選牌與推薦
- 右：分布、獎勵門檻、規則可信度

## 13. A11y

- 顏色不可作為唯一辨識；必須同時有文字「藍 / 紫 / 紅」。
- 所有卡片選擇皆能鍵盤操作。
- 互動元件有 focus state。
- 文字/背景對比至少 WCAG AA。

## 14. MVP 驗收案例

1. 兩張啟用藍卡只套用藍 2 張 +40。
2. 一張失敗倍率卡仍增加 SUM 20，而不是倍率。
3. 星星移除的卡同時從計分與顏色數移除。
4. 兩張倍率卡採加法，不彼此相乘。
5. 同 seed / 同輸入 / 同規則，推薦輸出一致。
