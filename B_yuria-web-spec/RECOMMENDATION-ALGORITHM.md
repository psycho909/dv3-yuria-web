# 尤里亞網頁版：目前推薦演算法

> 實作基準：`src/domain.ts`、`src/main.ts`、`src/recommend.worker.ts`、`src/real-game-record.ts`。本文描述目前**已實作**的行為，供日後依真實遊玩資料調整；較早的 `ALGORITHM-DATA-STRUCTURE.md` 包含尚未實作的規劃，不能代替本文判定現況。

## 1. 這個推薦回答什麼

玩家輸入目前已選的牌、每張牌的顏色和成功／失敗／移除狀態，再輸入本回合遊戲實際出現的三張候選牌及顏色。系統比較「現在點選其中一張，接著完成五回合」的可能最終分數，並依所選目標排序。候選牌的「獲得機率」是**點選後成功取得的機率**，不是出現在三張候選中的機率。

初始畫面為 0/5 張已選牌和三個空候選槽；三張不同且未在本局選過的候選牌填齊後才計算。推薦不會替玩家點牌，也不會把模型模擬局當成真實遊玩紀錄。

## 3. 最終分數如何計算

先排除已移除牌；其餘牌分成成功與失敗。顏色組合只計入**成功且尚未移除**的牌。失敗且未移除的牌每張加 20 分，但不提供自身卡片效果或顏色計數。

```text
SUM = 成功分數卡之和 + 20 × 失敗牌數 + 藍色級距 + 月亮效果 + 世界效果
MULT = 1 + 成功倍率卡加值之和 + 紫色級距 + 高塔／星星／太陽倍率加值
最終分數 = floor(SUM × MULT × (1 + RED_BONUS))
```

| 成功同色張數 | 藍色加分 | 紫色倍率加值 | 紅色最終加成 |
| ---: | ---: | ---: | --- |
| 0–1 | 0 | 0 | 0 |
| 2 | +40 | +40% | +10%～20% |
| 3 | +80 | +80% | +20%～30% |
| 4 | +160 | +150% | +40%～60% |
| 5 | +250 | +240% | +60%～90% |

目前預設紅色在對應區間內以**整數百分點等機率**抽取，端點也算入；例如兩張成功紅牌會抽 10%、11%……20%。分數只在整個乘積完成後向下取整。倍率卡與紫色、特殊倍率先相加，不彼此連乘；紅色加成最後再乘一次。例如兩張成功藍色分數卡分別 +100、+95，另有一張成功紫色力量，且沒有其他效果：`floor((100 + 95 + 40) × (1 + 0.8)) = 423` 分。

「尤里亞的祝福」目前**未納入**此分數公式；介面上的祝福門檻只是參考目標。紅色連續值與中間步驟取整等說法仍是待驗證假設，不會因單筆實測而偷偷改寫預設。

## 4. 第 1–4 回合：有種子的蒙地卡羅模擬

每張當前候選牌各跑預設 **10,000 次**（介面可選 5,000／10,000／20,000 次）。每次先依該牌的取得率判定成功或失敗，再模擬剩餘回合，最後依上述公式計分。使用固定種子 `20260922`，並以候選牌身分與顏色導出各自亂數序列；相同輸入與設定可重現相同結果。計算在 Web Worker 執行，避免阻塞畫面。

未來每回合先產生三張不重複、且不含本局已選卡片的候選牌，再由模擬策略挑一張。**這些未來候選並非已知的真實出牌**，其生成假設如下：

| 未來回合 | 分數：倍率：特殊的類別權重 | 顏色模型 |
| --- | --- | --- |
| 第 1–4 回合 | 10：10：5 | 每個候選位置獨立以 1/3 機率抽藍、紫、紅；同色可重複。 |
| 第 5 回合 | 5：10：20 | 同上。 |

在抽中的類別內，剩餘卡片等權；若類別已無可用卡片則改抽其他類別。上述權重與顏色分布是**模型假設**，不是從足量真實遊戲推定出的出牌率。

模擬中的未來第 1–4 回合，以單步「成功／失敗後預期當下分數」的貪婪策略選牌；高塔的兩種倍率和星星的可能移除目標也會平均納入。模擬走到第 5 回合時，在目前預設的整數紅色模式下，會比較三張牌的精確最終分數分布，先看達標率、同率再看平均分。即使畫面目前選的是「預期分數」或「穩定」，**未來第 5 回合的模擬策略仍依目標分數選牌**；畫面的模式只決定當前三張候選的最終排序。這是有限步近似策略，**不保證五回合全域最優**。

## 5. 第 5 回合：完整列舉

目前預設整數紅色模式下，最後一回合不用抽樣：逐一列舉候選牌的成功／失敗、高塔成功後 50%／50% 分支、星星各個可移除目標，以及每個可能的紅色整數百分點，並依各分支權重合併同分結果。這時 `method = exact`、`simulations = 0`。所謂「精確」是**在目前卡牌資料與規則假設之內**的精確分布，不代表遊戲真實機制已全部驗證。

## 6. 指標與排序

每張候選顯示：達到自訂目標分數的機率、預期最終分數、P10／P50／P90、最小／最大模型分數，以及該卡點選後的取得率。P10 可理解為較保守的結果門檻；它不是「卡片取得率」。

| 模式 | 排序規則 |
| --- | --- |
| 達標率（預設） | 達標率高者優先；同率時預期分數高者優先。目標預設 1,500 分，可自行輸入。 |
| 預期分數 | 平均最終分數高者優先。 |
| 穩定 | P10 高者優先；同率時預期分數高者優先。 |

若達標率模式下三張候選的達標率全為 0，會改以**預期分數最高**排序。前四回合的「0」只表示這次有限抽樣未命中，不可宣稱實際機率必為 0；第 5 回合的「0」表示目前列舉模型內沒有達標結果。

## 7. 真實紀錄、AI 邊界與後續調整

五回合完成並由玩家按下「紀錄本局」後，才建立正式真實牌局紀錄。遊戲實得分數可留空，並與模型分數分開保存。紀錄包含每回合候選、選擇、顏色、結果、特殊卡分支、當時預測、規則快照、牌庫版本、種子與模擬次數；更正會留下修訂資訊。`catalogProbability` 是牌庫設定的點選成功率，`observedProbability` 在沒有實測統計前為 `null`。歷史上只有總分的五局、模型自我模擬的三十局，均不可冒充完整真實牌局。

目前 B 網頁版**沒有呼叫 Jev 來算數學或選牌**；目標模式由畫面選擇，分數、機率與排序皆由本機 `domain.ts` 決定。A 原型的 Jev 僅可作語意目標路由，不可取代確定性機率與計分程式。

後續調整應先收集足夠真實完整牌局，再逐項驗證：未來出牌類別與類別內權重、顏色分布、星星移除目標、太陽是否計自身、紅色取樣／取整規則和祝福公式。變更規則時保留明確的規則選項與版本，對已知實測牌局做回歸核對，並比較達標率校準、分數誤差與效能；不能只因單次推薦失敗就修改機率。

## 8. 程式與驗證入口

- `src/domain.ts`：22 張牌、規則、計分、未來出牌、模擬與排序。
- `src/recommend.worker.ts`：瀏覽器背景計算入口。
- `src/main.ts`：候選輸入、推薦模式、畫面呈現與五回合操作。
- `src/real-game-record.ts`：真實牌局資料結構、驗證與版本快照。
- `tests/`：計分、特殊卡與推薦回歸測試；執行 `npm test`、`npm run typecheck`、`npm run build`。
